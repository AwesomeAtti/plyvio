The dialog reads nothing — and what that leaves to build

No username check, no game counts anywhere, no detecting that a paste contains no chess. Each removal was right on its own; together they change the dialog's nature. It never opens a PGN at all.

Which makes it a form. It collects a source and some options, hands them to the import, and closes. Everything that requires looking at a game happens in the lane, and everything that can go wrong is an import error. The second half of this document is the answer to your last question: what is left to build a click-through mockup, and which parts are blocked.

The dialog is now a form, and the read band has nothing to report

The read band existed to say what I found when I looked. Nothing looks any more, so on two of the three tabs it would only repeat the controls directly above it — the Online line said chess.com — AwesomeAtti · all time under a form that already said exactly that, and the Paste line named a text area the user is looking at.

So the read band survives only on the File tab, where it is not a read at all: it is the list of files, and a list is the only way to show several of something. The dialog's anatomy drops from four bands to three.

2 · The two revised tabs

Suggested Keep the subscription list

Removing the verification left the Online tab with a form and empty space below it. Listing the subscriptions that already exist fills it with the one thing the user might otherwise get wrong — asking for something they already receive automatically.

It is local data, needs no network, and answers the "already subscribed?" question that r4 handled with a lookup. Purely informative: nothing is clickable.

Alternative Leave the space empty

The form sits at the top of the source band and the rest is whitespace.

Defensible — the dialog is a form and forms are allowed to be short. But it is the only tab with a visible void, and a void invites the question of what should be there. The list is a cheaper answer than shrinking the dialog for one tab.

3 · What moved into the import

The failures the dialog used to catch are now outcomes the import reports. They are whole-source failures rather than per-game ones — nothing was added from that source at all — and they say so in one sentence, the same sentence every time.

One outcome: No games found

A misspelled username, an account with nothing in the chosen range, a paste that turned out to be an email, a .pgn holding only comments — these are the same outcome and get the same words. The causes differ; what the user is told does not, because nothing they could do about it differs either. They check what they gave it.

It is also the only honest option now that nothing is verified: the import has a source that yielded nothing, and in most of these cases it cannot tell which reason applies — an API that returns an empty list looks identical whether the account is empty or absent.

SourceMessageCovers
FileNo games found in notes.pgnEmpty file, comments only, not PGN at all
PasteNo games found in the pasted textProse, a broken copy, the email around the games
OnlineNo games found for AwesomeAtti on chess.comNo such member, empty account, nothing in the chosen range

The source is still named — that is identification, not diagnosis. With three files chosen, "No games found" alone would not say which one, and naming it costs nothing and explains nothing.

The two outcomes that stay separate, and their names

Both are cases where the source was never read at all — so "no games found" would describe a search that never happened. Each is named for the thing that went wrong, in two words, matching the brevity of the message they sit beside.

NameMessageWhen
File errorFile error — twic1600.pgn could not be opened Missing, moved, permission refused, a directory. The next move is find the file, not check its contents — and this is the one case the import knows for certain.
Network errorNetwork error — download did not complete · Try again The connection dropped mid-download. Nothing was written and nothing was wrong with the request, so this is the only failure in the design with a one-click remedy.

Three outcomes in total, then, and a user can tell them apart at a glance without reading past the first two words: No games found · File error · Network error. Only the third offers an action.

A whole-source failure is not a partial success. Under the r3 §4 scope rule an import fails only if every source failed — so three files where one is empty is still a successful import with a note, and a paste with no games is a failed import, because the paste was the only source. The result of an import needs to distinguish those two, whatever form it eventually takes.

4 · The result, without a banner

The layout objection settles this. A banner between the toolbar and the Content Table shifts the table twice — down when it appears, up when it is dismissed — in a region the user may be scrolled in, and it arrives at a moment they did not choose. Every alternative that avoids the shift introduces an overlay the application does not have.

Recommendation — no banner. The Status Bar carries it, and the Library itself is the receipt

A clean import does not need announcing. The table fills with the games, the count climbs, the Sidebar moves to Recently Added, the tag and collection appear as Sidebar rows. That is a more informative report than a sentence, and it is already on screen.

The exception does need persisting — and the Status Bar's right slot already holds it, at rank 2 of the precedence in r2 §2, surviving Sidebar changes and searches until it is answered.

Nothing new is built, nothing shifts, and a banner can still be added later if the mockup shows the finish is too quiet. Adding one later is easy; removing one is not.

The two timings this needs

NoticeLifetimeDismiss
Import finished, cleanabout 8 secondsNone — it removes itself. Nothing is lost if it is missed, because the Library already shows the result.
Import finished, problemsuntil answeredClicking it opens the report; the close control dismisses it unread. Survives Sidebar changes, searches, and switching tabs and back.

The one case worth watching in the mockup: a first import into an empty Library. There the Content Table was showing §3.2.4.2's empty state, so the change from "No games in your library" to 3,000 rows is the largest confirmation the application can give — and the argument for silence is at its strongest. If a banner is ever wanted, it is for the opposite case: a 12-game import into a library of 40,000, where nothing visibly changes.

5 · What is left to build a click-through mockup

The answer is: four of the five screens are fully specified, the interactions are all synchronous or fakeable, and the only blocked piece is the last one. Below is the inventory, in the order it would be built.

ScreensStatus

Fixtures — the fake data it needs

  • A game list — the prototype already generates one.
  • Databases — three or four, one disabled and one indexing, so the destination dropdown shows §3.2.3.10's non-selectable states.
  • Tags — a dozen, including two that share a prefix, so filtering is visibly doing something.
  • Collections — half a dozen, including two Smart Collections that must not appear in the picker. Without them in the fixture the exclusion rule is untested.
  • Subscriptions — one, so the Online tab's list has a row and the "already subscribed" case is reachable.
  • Import scenarios — clean · slow · cancelled · online two-phase · connection lost. Each is a script of timings, not data.

What the mockup would settle that drawings cannot

  • Whether the modal is right at all. Three revisions have flagged the missing modal layer as the largest cost in this direction. A click-through is the cheapest way to find out whether a dialog over the Library feels correct before the shell gains a layer it cannot easily lose.
  • Whether the two tab strips collide (AG‑D‑5's open risk) — 60px apart, in motion, on a real screen.
  • Whether three option rows feel heavy for a user who wants none of them.
  • Whether the status bar is noticeable enough to carry the only progress in the application.

6 · What is still parked

One thing, and it no longer blocks anything: the Class 2 policy — whether a game with an illegal move is rejected, truncated and kept, or imported unvalidated (r3 §5).

It decides the import report's contents, not its shape. Under P‑1 the report is one list of games that were not added; under P‑2 that list gains a second section above it for games that were added but truncated. A mockup built on the one-list version needs no rework to gain the second — it is another group header in the same scroller.

Nothing is blocked

All five screens can be built now. The banner question is answered by not having one, and the Class 2 policy changes a list's contents rather than any screen's structure.
