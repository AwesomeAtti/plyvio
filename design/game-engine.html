4 · Scope — a live view, not a game-analysis feature

Corrected 21 Sep

This Section shows a live evaluation of the current position only, for as long as it's on. It has no write path to [%eval] and no relationship to whether one exists: it runs the same way whether the game carries persisted evaluations or not, whether they came from the same engine selected here or a different one, and whether they're stale or current. It doesn't read them to decide what to show, and it doesn't produce them.

A feature that walks a whole game and computes or rewrites [%eval] for every move — batch or on-demand game analysis — is a genuinely different feature. It isn't drawn here, isn't proposed here, and this Section's design doesn't assume it's coming. Q7 asked a question shaped by that other feature and has been withdrawn rather than answered as asked — see §6.

5 · Reading the spec's own open thread

§5.4.1 (Evaluation Bar) doesn't just leave this Section undrawn — it explicitly hands it three unresolved questions: “The bar's source priority, its retention behaviour when an engine stops, and its relationship to any Section reporting evaluations are specified with the Engine Section.” None of the three are decidable from your concept alone, so they're carried into §6 rather than guessed at here. §4's scope correction bears directly on all three: whatever the Bar ends up doing, this Section is a read-only, ephemeral source to it — never a writer of [%eval], regardless of how the questions below resolve.

6 · Questions — before this can pass G1

  1. Q1 · settled 21 SepsupersededDoes the control stay the shared icon button, or become a switch?

    Superseded in the Game Info round — game-info-g1.html. The control is the shared 26px icon button after all, carrying Lucide’s toggle-left / toggle-right. The Section Header now has no exceptions: every Section fills the same slot with the same widget.

    The exception closed on its own argument rather than against it. What Q1 objected to below was the glyph — a power symbol “shows what pressing it does while showing nothing about what it is doing now” — and a toggle draws the state instead of describing it: the knob’s position is the answer. That was the one thing the icon button could not do, and it can now do it. Everything the answer below says about why a watched state is not an action still holds; it is why the glyph is a toggle rather than why the widget is a switch.

    Built and verified. The button keeps role="switch" and aria-checked — the picture changed, not the semantics. Running is drawn in --ok, keeping the across-the-panel reading the green switch gave.

    The glyph is drawn at 20px where the header’s other icons are 13, decided after rendering it at 13, 15, 16, 17, 18 and 20 on the real 360px header. Not because it fails small — at 13px the knob’s position is distinguishable, and the colour carries it besides. Because this is the only control in the panel that reports an ongoing state: the ellipsis and the chevron are read when the reader goes looking for them, and this one is read while a search is running, at a glance, from wherever the eye happens to be. Legibility at a glance is worth more here than uniformity with glyphs that are only ever read on purpose. The 26px button is unchanged, so the control column does not move; what differs is the mark inside it.

    Still to do at G3: §5.4.2 names this exception in prose (“One exception is specified…”) and §5.6.4’s derived table repeats it (“Engine control — A switch, and the only exception to the shared Section Header”). Both need retiring, and the reasoning is worth keeping as why the glyph is a toggle rather than deleted with the exception it used to justify.

    What was decided on 21 Sep, kept as the record:

    Keeps the switch, documented as an exception. It genuinely diverges from the pattern, and not in the way hiding status does. Status being optional is variation the pattern already accounts for: §5.4.2 lists Source, Status and Control as each independently optional, and Explorer and Timeline already show it's normal for one Section to use a slot and another not to, or for the same slot to carry different content (a game count, an evaluation). That's presence and content varying. The widget itself never has — every Section that has ever drawn a status shows it as the same muted mono text, every source as the same truncating button-plus-chevron. The spec is explicit about why: the header is “a common Section Header… which Sections fill in rather than reinvent.” A switch is a second widget for a slot that has, so far, only ever had one shape.

    The case for keeping it anyway: Control has no real precedent yet to diverge from — Engine is the first Section to ever populate the slot. GameSection.svelte's generic icon-button rendering is a placeholder default, written before any Section asked for a control, not a decision reached by designing one. And “is this on” is a different kind of control than “open this menu” or “collapse this Section,” reading faster as a switch than as a button with two icon states.

    Treated the way §7.4 treats a Lucide exception: deliberate, named, and recorded here rather than slipped in silently, so a future Section that also wants a control isn't left guessing which precedent it's supposed to follow — the generic icon button remains the default for everyone else. At G2, GameSection.svelte needs a per-Section override for Engine's control rather than the one branch every other control renders through.

  2. Q2 · settled 21 SepCan the Section be “on” with no engine selected?

    No. The control is disabled whenever the source reads “No engine” — EN-04 already drew it that way and turns out to have been right. If a future source list offers an explicit None entry the way Explorer's library source does, selecting it forces the control off the same way. If MultiPV/depth/etc. should persist per engine choice, that's still a live question for EN-05, but it no longer blocks trusting this rule.

  3. Q3 · settled 14 SepWhat goes in the status slot?

    Nothing. I'd proposed the top line's depth (d28) so the search's progress was readable without opening a row; withdrawn — depth stays where it already is, per row, and the header shows title, source, control, options and collapse only (EN-02, EN-05). What's still open is narrower: sections.js declares status: true for this Section, and with nothing proposed to put there, that flag may want to come off entirely rather than stay reserved for a slot that's always empty — a small G2 cleanup, not a wireframe question, unless something else earns the slot first.

  4. Q4 · settled 21 SepAre PV rows interactive?

    No — rows report, they don't do anything when pressed. The current app is a viewer for played moves: it doesn't edit or create them. Clicking a PV row to create a variation, or to play the suggested move onto the board, belongs to interactive analysis — on the roadmap, not in scope now, the same relationship Move Explorer already has with a future analysis board of its own spec. This Section joins Explorer in “reports; does not navigate” rather than being a second, narrower exception to it.

    Concretely: no hover state, no cursor change, no board-arrow preview on a PV row. EN-02's rows are drawn correctly as-is — nothing there implied interactivity, so nothing needed redrawing.

  5. Q5 · settled 21 SepDo MultiPV/threads/hash belong in this Section at all?

    Engine settings belong in Settings. This Section's options menu isn't a second configuration surface — it surfaces the couple of settings worth reaching mid-analysis for convenience, and only those. Named explicitly: lines (MultiPV) and depth. Threads and hash are dropped from EN-05; they stay a Settings concern and aren't drawn here at all.

    That leaves a real gap on the Settings side, worth naming rather than quietly working around: spec/database-schema.md §5.3 is explicit that the engines table stores only name, version, URL and binary path — “analysis settings such as search depth, threads, or hash size” are named as out of scope for it, and reusable engine profiles are floated only as a maybe, modeled separately if they happen at all. Wherever threads and hash end up living, it isn't decided yet and it isn't this document's decision — it belongs to whatever draws that part of Settings, not to this Section for lack of anywhere else to put them.

    Depth is worth flagging as a name overloaded twice already. EN-02's rows already show reached depth per line (d28, live, read-only). EN-05's depth limit is a different thing — the search's configured ceiling, the depth in go depth N and the same attribute the PGN Engine Evaluation Context Extension calls depth for a stored analysis. Same word, two meanings already in this one Section; the options row is labelled “Depth limit” rather than bare “Depth” so the two don't get read as the same number.

    Max lines — settled 21 Sep, option A: capped at 3, the same number and the same reasoning Move Explorer already used for its own ceiling — a position has a point past which another row stops earning its space, and three is where Explorer already drew that line for candidate moves. Ties this Section's ceiling to Explorer's exactly: 108px for both. See Q6 for the arithmetic.

  7. Q7 · withdrawn 21 Sep, wrong premiseDoes analysis restart on every ply, or only the current one?

    This question assumed a feature that isn't this Section: something that walks the game and computes or rewrites [%eval] across many moves, where “does it restart per ply” would be a real cost/design tradeoff. That's a game-analysis feature and it's a different thing entirely — not drawn here, not proposed here, not on this Section's roadmap as far as this document goes.

    What this Section actually is: a live view of the current position, full stop. It never writes an [%eval]. It has no relationship to whether the game carries persisted evaluations at all — it can run with none present, alongside ones from a different engine entirely, or alongside ones from the same engine, and none of that changes what it shows, because it isn't reading them either. Given that, the question this was reaching for isn't really open: the Section shows the current position by definition, so when the current position changes — the transport steps to a new ply — what it's live-analyzing changes with it, the same way the board itself does. There's no separate “hold still until pressed again” mode to weigh against that; holding still would mean it stops being a live view of the current position.

  8. Q8 · settled 21 SepThe Evaluation Bar relationship (§5), concretely

    Loose, not owned. The bar and this Section stay two separate displays that happen to agree when they can — the bar never becomes a mirror this Section drives, and this Section never reads the bar's value either.

    Section stateBar shows
    Running, for the current positionThe live top-line evaluation — and it may visibly move as the search deepens, the same way the bar already animates between plies (§5.4.1's existing transition, not a new one).
    Off (or never run here), [%eval] presentThe persisted evaluation, exactly as before this Section existed.
    Off, no [%eval]The documented neutral fill (§5.4.1) — unchanged.

    Never both. Live and persisted are never shown together or blended — one or the other, by whether this Section is actively running for the position on screen right now.

    Retention has two different answers depending on what you're asking about, which is exactly why it needed spelling out:

    • Turning the switch off does not clear this Section's rows. The last computed lines stay on screen, same position, switch visibly off — EN-06. The bar still reverts to [%eval]/neutral immediately per the table above; only the Section's own display lingers.
    • Stepping to a different ply does clear it — on or off, the data belonged to the position you left. Returning to that same position later shows nothing, not a recalled result: live data doesn't persist across navigation, at all, ever. There's no per-position cache to warm.
